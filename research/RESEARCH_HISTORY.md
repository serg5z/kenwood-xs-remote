# Kenwood XS8 research history

The archive documents a progression from passive observation of a KR-V6070 receiver and connected CD player to an Arduino transmitter, context aware command mapping, and a CEC to XS8 bridge. The strongest evidence is for the bus timing, a working transmit method, and several state dependent responses. Most of the large command maps are recorded bench observations: the archive does not contain a raw log of the later controlled sweeps, so their visible hardware effects cannot be independently replayed from the captures.

## Byte conventions used in this report

This distinction is essential when comparing the notes:

| Label | Meaning |
|---|---|
| **Waveform** | Recorded DATA and BUSY transitions and their timing, before assigning byte values. |
| **Legacy byte** | Earlier MSB first presentation, with short DATA low = `1` and long DATA low = `0`. The passive sniffing note and older TX scanners use this convention. |
| **Logical TX byte** | Later LSB first transmit presentation, with short DATA low = `0` and long DATA low = `1`. The bridge uses this convention. |

For the *same transmitted waveform*, `logical = reverse8(~legacy)`. Thus legacy TX `DE` is logical TX `84` (CD selection in ROOT); legacy `60/68` are logical `F9/E9` (volume up/down). `17` happens to retain the same value under the conversion. The old scan’s TX `57` is logical TX `15`, while logical TX `57` is a different waveform. [Mapper convention](/Users/serg/projects/kenwood-xs-remote/research/sketches/xs-tx-test1.ino:1), [reviewed convention](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:9)

**RX labels need their own care.** The later `xs-tx-test2.ino` sends logical TX bytes but explicitly retains the older physical/MSB first representation for received frames such as `DE`, `D2`, `D6`, and `7D`. Consequently, a notation such as **TX `84` → RX `7D`** combines a logical TX label with a legacy style RX label. It is evidence of a response, not a claim that both printed values use one byte convention. [RX decoder comment](/Users/serg/projects/kenwood-xs-remote/research/sketches/xs-tx-test2.ino:350)

## Chronology of discoveries

1. **Pin mapping and passive capture, 7 October.** The working setup identified TRS sleeve as ground, tip as BUSY, and ring as DATA. Edge and ADC capture established a BUSY envelope, DATA start pulse, and approximately 4.9/9.8 ms low intervals followed by approximately 4.9 ms high intervals. The early sniffing note corrected an initial framing mistake and presented captured bytes MSB first, without reversing or inverting its *own* decoded byte. With the CD stopped or off, receiver front panel source actions gave repeatable legacy labels, including CD `82`, TUNER `84`, TV1 `85`, TV2 `8E`, and alternating TAPE2 `EB/E7`. Starting CD playback yielded changer `DE`, then receiver `7D`; pause and stop yielded `D2` and `D6`. NEXT/PREV during playback produced no observed XS traffic. These observations led to the system coordination model: playback could cause receiver CD selection, while selecting CD at the receiver could start an available changer. [Sniffing note](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs8-sniffing-notes.md:8)

2. **Electrical tests and active transmission.** The experiments moved from voltage measurement and pin tests to literal waveform replay and byte scanners. The eventual working Arduino Micro arrangement used D2 through 2.2 kΩ to DATA, D3 through 2.2 kΩ to BUSY, and A0/A5 to sense those lines. Its TX pins drive HIGH and release to INPUT/high impedance for LOW; it waits for an idle BUSY line. The nominal frame begins with BUSY rising, DATA rising about 1.15 ms later, and a roughly 9.8 ms DATA start pulse. Earlier active LOW replay sketches remain useful records of what was tried, but they do not define the bridge’s electrical method. [Electrical summary](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:55), [working send routine](/Users/serg/projects/kenwood-xs-remote/xs8-bridge/xs8-bridge.ino:39)

3. **Brute force scanning exposed state.** Legacy scanners found receiver source selection, CD transport, tuner controls, volume hold, and commands that altered subsequent interpretation. The archived state aware scan tested candidates `00` through `17` before stopping: after legacy TX `17`, its usual legacy `DE` CD probe and `57` “recovery” ceased to respond. That log directly supports a state change at `17`; it does **not** establish that `57` was a generic recovery operation or document completion of a `00–FF` sweep. [Scan setup and stop](/Users/serg/projects/kenwood-xs-remote/research/captures/kenwood-xs-scan.txt:29), [final candidate](/Users/serg/projects/kenwood-xs-remote/research/captures/kenwood-xs-scan.txt:499)

4. **Context and control state were separated.** Early notes called `17` “ENTER TUNER” and legacy `1F` “EXIT TUNER,” based on tuner like behavior: notably legacy `DE` selected CD normally but preset CH8 after `17`. Later controlled tests used logical TX bytes and found `x13` returned source/monitor status in ROOT, became silent after `x17`, and worked again after **`x07`**. Logical `x1F` did not restore ROOT. This matters because `x07` also failed to release a separate front panel lock; context exit and lock release are distinct observations. The later interpretation leaves the *semantic name* of the `x17` context open. [Early model](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering.md:9), [revised tests](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:26)

5. **Controlled ROOT mapping and targeted `x17` work, 8–9 October.** The notes report a full one byte sweep with ROOT, CD selected, and CD playing. It found direct track commands `x18` through `x98`, source controls, CD transport, status queries, and a family of bytes that left front panel controls locked. In ROOT, `x13` returned a source identifying first RX and a monitor dependent second RX (`18` off, `14` on); `x14` gave the same pair in the tested ROOT+CD state. `x15` released the observed lock, while many `*5/*6` codes could set it. Targeted `x17` tests found tuner presets at `x04`, `x14`–`x94`, band at `xB4`, tune at `xE4/xF4`, and continuous volume down/up at `xE9/xF9`, stopped by `x09`. Several CD actions still worked in `x17`, sometimes with a TUNER input side effect. [ROOT sweep](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:210), [targeted context findings](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-v18.md:508)

6. **CEC bridge.** The committed host program accepts libCEC volume and mute key events and sends one character commands over USB serial. The Arduino bridge turns them into logical XS8 sequences: volume up `17 F9 … 09 07`, volume down `17 E9 … 09 07`, and mute `17 D8 07`. Host and Arduino watchdogs address a missed volume release; the firmware records that it cannot send STOP while BUSY remains permanently occupied. The commit describes the bridge as hardware validated, and the code clearly implements the discovered sequence. No CEC session log or measured end to end test result is archived here, so that validation claim cannot be independently checked from the repository. [Host implementation](/Users/serg/projects/kenwood-xs-remote/main.cpp:1), [Arduino bridge](/Users/serg/projects/kenwood-xs-remote/xs8-bridge/xs8-bridge.ino:1)

## Interpretations that changed

| Earlier interpretation | Later evidence and present reading |
|---|---|
| Reverse or invert the passive capture to recover its byte. | The sniffing note attributes that mistake to counting framing as data. Its MSB first, short=`1` decode stands as a **legacy presentation**. The later LSB first, short=`0` logical TX presentation deliberately changes labels for the same waveform; the conversion reconciles them. [Sniffing correction](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs8-sniffing-notes.md:19), [TX conversion](/Users/serg/projects/kenwood-xs-remote/research/sketches/xs-tx-test1.ino:178) |
| `x17` definitively enters a TUNER only context. | Tuner operations were observed, but CD transport continued to work after `x17`. A broader device/subcommand context remains possible. `x13` silence and changed `x84` behavior establish altered interpretation, not the context’s protocol name. [Reviewed model](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:26), [cross context tests](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-v18.md:537) |
| `x1F` exits the context; `x07` does not recover it. | Later A/B probes show logical `x07` restores ROOT status and source behavior, while logical `x1F` does not. The older `x07` failure concerned releasing a **lock**, not restoring command context. [Copy 6, earlier claim](</Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering copy 6.md:63>), [Copy 6, corrective observation](</Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering copy 6.md:487>) |
| Legacy `57` was a source recovery command; legacy `11` was a source lock. | Legacy `57` maps to logical `15`, whose observed effect is release of a locked control state and status like RX even when already unlocked. Legacy `11` maps to logical `77`, one of many lock producing bytes. Their higher level semantics remain unknown. Logical `57` is a different command. [Early scan labels](/Users/serg/projects/kenwood-xs-remote/research/captures/kenwood-xs-scan.txt:30), [lock observations](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:177) |
| `x8A` was previous disc; `xEC` previous track; `xFC` repeated skip. | The controlled ROOT sweep records `x8A` as **next disc**, `xEC` as continuous previous track style behavior, and `xFC` as continuous next track style behavior. `xE5/xE6` advanced from “appears to play from beginning” to observed current disc restart. [Copy 5 tentative map](</Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering copy 5.md:429>), [reviewed corrections](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:272) |
| Every `D6` RX means STOP acknowledgment. | STOP can be followed by delayed `D6`, but `C3/D3/E3` produced nearly immediate `D6`, and a second CCRS activation did too. Treat `D6` as an unresolved changer report. [Timing comparison](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:302) |

## Verified behavior and evidentiary limits

**Directly present in archived machine records:** the CSV edge transitions support the BUSY/DATA waveform and timing; `xs-amplitude.csv` records a measured high level for its particular measurement setup; the partial serial scan records TX labels, RX labels, timing, and the `17` state change up to its stopping point. Sketch code proves what the instruments *would log* and what the bridge *would transmit*, but code alone does not prove a receiver reaction. [Waveform capture](/Users/serg/projects/kenwood-xs-remote/research/captures/xs-session2.csv), [partial scan](/Users/serg/projects/kenwood-xs-remote/research/captures/kenwood-xs-scan.txt:499)

**Reported as controlled hardware observations in notes, without retained raw logs:** the full ROOT matrix; source and monitor responses to `x13`; `x14` matching `x13` in ROOT+CD; persistent control lock and `x15` release; `x07` restoring ROOT; tuner presets and receiver controls in `x17`; and the ROOT versus `x17` `x8A` side effect. These are stronger than guesses because the notes describe state controls and repeat tests, but a future author cannot independently audit each event’s waveform or physical display state. [Reviewed sweep baseline](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:210), [targeted A/B](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:470)

**Inferred semantics:** names such as “status query,” “context,” “release,” “changer event,” and “CCRS start” summarize observed patterns. They are not established protocol definitions. In particular, an RX absence is not proof that a byte does nothing, and the broad ROOT sweep applies to its stated **ROOT + CD + playing** baseline. [Documentation caution](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-v18.md:564)

## Material disagreements within the notes

- **Context exit:** [the base note](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering.md:38) says `0x1F -> EXIT TUNER context`; [copy 7](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering%20copy%207.md:70) says `0x07 -> EXIT` and `0x1F -> does NOT exit`. The later `x13`/`x84` probes favor `x07` for the tested context.
- **Lock scope:** [copy 2](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering%20copy%202.md:39) describes a `0x77` *input-selection* lock; [copy 7](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering%20copy%207.md:39) reports `0x67` and `0x77` locking *all front-panel buttons*. The later clean tests broaden the observed effect; they do not establish either byte’s formal command name.
- **Disc direction:** [copy 5](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering%20copy%205.md:429) says `8A = previous disc`; [reviewed](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:277) explicitly says `x8A is NEXT DISC` and calls the earlier label wrong.
- **Pause report:** [the passive note](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs8-sniffing-notes.md:79) records PAUSE as `D2`; [the active sweep note](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:331) records RX `DA` when `xBC` pauses and explicitly leaves the discrepancy unresolved. It may reflect different initiators or states, but the archive does not decide why.
- **Scope of a “complete” sweep:** [the base note](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering.md:278) says a full `00–FF` brute force sweep was completed; [the only archived serial scan](/Users/serg/projects/kenwood-xs-remote/research/captures/kenwood-xs-scan.txt:499) stops at `17`. Later notes report a separate controlled full sweep, but its raw session log is absent. These statements should be kept with their respective experiments, rather than treating the partial capture as evidence for all 256 later cells.
- **RX notation in the late notes:** [reviewed](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:9) broadly says bytes are current logical unless marked legacy, while [its ROOT matrix](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:272) prints responses such as RX `7D`; [the receiving sketch](/Users/serg/projects/kenwood-xs-remote/research/sketches/xs-tx-test2.ino:350) says RX retains the older representation. The sketch is the clearest guide to interpreting those response labels.

## Open questions

1. What does `x17` mean at the protocol level: tuner addressing, a generic component context, or another mode? Does another context require a sequence rather than one byte?
2. What causes the receiver to select TUNER after some changer actions in `x17`? The `x8A` A/B demonstrates the side effect, but does not identify the responsible device.
3. What precisely do changer reports `D6`, `D8`, `DA`, and `DE` encode? Why does passive pause yield `D2` while active pause yielded `DA`?
4. What is the semantic distinction among the ROOT lock producing bytes, and what broader function might `x15` release? The observed lock state is established; the command names are not.
5. What are the exact numeric mappings, completion, cancel, and exit behavior for direct frequency and direct channel entry? Earlier exploration mixed submodes.
6. Which apparently silent codes have effects outside the tested source, playback, monitor, or changer configuration? No RX and no recorded visible action leave this open.
7. How closely must a replacement transmitter match the Kenwood frame tail and electrical levels across hardware variants? The bridge’s DATA first release and guard interval are working experimental choices, not a measured universal requirement.
8. Can the bridge’s reported hardware validation be reproduced with an archived CEC and serial trace? The implementation and commit record exist; a test trace does not.
