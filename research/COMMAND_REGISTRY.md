# Kenwood XS8 command registry

The registry records each byte by direction, context, and tested state. A sequence has its own row linked to its constituent bytes. That prevents `x84` in ROOT from overwriting `x84` after `x17`, and prevents an RX report from being treated as a TX command.

| Field | Registry rule |
|---|---|
| Byte | Store current **logical TX** value for transmissions; retain any documented legacy TX value in a separate field. Store RX exactly as printed by its decoder. |
| Direction and notation | Specify `TX · logical`, `TX · legacy original`, or `RX · legacy decoder`. Early passive RX labels need an additional “early sniffer” qualifier. |
| Context and state | Record ROOT, observed `x17` context, or unknown, plus source, playback, monitor, lock, and changer connection where known. |
| Observation | Describe a visible action, recorded response, or absence of a response. Keep a proposed protocol meaning in a separate field. |
| Confidence | **OBSERVED** = a hardware observation reported in the archive, with the evidence type stated; **INFERRED** = interpretation beyond that observation; **UNVERIFIED** = library definition, tentative impression, or behavior without a confirming test. |
| Conflict | Link the contrary observation or unresolved state dependence. An empty conflict field must not imply exhaustive testing. |

The conversion for a **TX waveform** is `logical = reverse8(~legacy)`. For example, legacy TX `DE` → logical TX `84`; legacy `60/68` → logical `F9/E9`; legacy `1F` → logical `07`. **Do not apply that conversion to RX values in this registry.** The later test sketch explicitly retains MSB first, short low = `1` decoding for RX while sending logical TX bytes. [Conversion](/Users/serg/projects/kenwood-xs-remote/research/sketches/xs-tx-test1.ino:178), [RX decoder](/Users/serg/projects/kenwood-xs-remote/research/sketches/xs-tx-test2.ino:350)

“OBSERVED” below means *reported from a hardware test*, unless a row explicitly cites a retained serial capture. The complete later sweep is documented as a matrix, but its raw test log is not archived. The retained [state aware scan](/Users/serg/projects/kenwood-xs-remote/research/captures/kenwood-xs-scan.txt:29) covers only candidates `00–17` and stops at `17`.

## Byte Encoding and Decoder History

- **Legacy TX:** MSB-first, short DATA LOW = `1`, long DATA LOW = `0`.
- **Current logical TX:** LSB-first, short DATA LOW = `0`, long DATA LOW = `1`.
- **TX conversion:** `logical = reverse8(~legacy)`. This converts labels for the same transmitted waveform; it does not change the waveform. The reverse operation has the same form.
- **RX history:** Early and later RX source labels appear to differ by bitwise complement—for example, early CD `82` and later CD `7D`, or early TV2 `8E` and later TV2 `71`. That is consistent with a decoder polarity change. The exact historical cause is **UNVERIFIED** until checked against the original sketches and capture paths. [Early source labels](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs8-sniffing-notes.md:33), [later broadcasts](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:143)
- **Registry rule:** Preserve original RX byte values and name the decoder convention (“early passive sniffer” or “later legacy RX decoder”). Do not silently complement, reverse, or otherwise normalize RX. The later RX routine explicitly preserves the MSB-first, short-LOW=`1` presentation. [Later RX routine](/Users/serg/projects/kenwood-xs-remote/research/sketches/xs-tx-test2.ino:350)

## Remaining ambiguities and registry exclusions

- **Early passive versus later RX source labels:** `8E` versus `71`, `82` versus `7D`, and the other shared source pairs differ by bitwise complement. This is visible from the notes, but the archive does not explicitly establish a universal conversion between those RX decoders. Preserve both label sets.
- **Context versus audio input:** `x17` changes command interpretation; changing receiver source does not necessarily leave that context. CD transport can continue after `x17`, sometimes alongside tuner selection. The source-selection mechanism and `x17`’s protocol meaning remain unknown. [Context follow-up](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:470)
- **Conflicting historical commands:** Earlier `NORMAL` labels for converted `x38/x48/x78/x88` disagree with the controlled ROOT+CD track family. State and possibly decoder history are not fully recoverable. Keep historical entries with their own evidence rather than selecting a single global meaning. [Legacy list](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:429), [controlled tracks](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:284)
- **Negative cells:** The ROOT `00–FF` matrix contains many dots, and the targeted `x17` map contains RX-silent cells. A dot means no effect recorded under that test’s conditions. The proposed registry should preserve sweep coverage as a **test-result record**, without manufacturing 256 “NOP commands.” [ROOT baseline](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-reviewed.md:210), [`x17` caution](/Users/serg/projects/kenwood-xs-remote/research/notes/kenwood-xs-reverse-engineering-v18.md:508)
- **Changer reports:** `D6`, `D8`, `DA`, `DE`, and the isolated `35` have observed associations but no established field definitions. `D2` versus `DA` on pause remains unresolved.
- **Direct entry:** `x25` and `x75` have observed tuner-related effects after `x17`; a complete digit map, mode transitions, cancel, and completion sequence are not established. No missing digits have been filled from numerical patterns.
- **Bridge evidence:** The firmware and host code define real sequences, and the project history calls the bridge hardware validated. The sources supplied here contain no retained CEC-to-serial-to-XS trace proving the complete chain. [Bridge](/Users/serg/projects/kenwood-xs-remote/xs8-bridge/xs8-bridge.ino:1), [research history](/Users/serg/projects/kenwood-xs-remote/research/RESEARCH_HISTORY.md)
- **Generic KEY RELEASE remains unproved:** ROOT `x9C` has stopped playback and was historically reported to stop an `xFC` forward-skip run; the new `x41 → x9C` trial confirms a PLAY-to-STOP result only. ROOT `x15` releases a control lock, entered-context `x09` stops volume, and entered-context `x07` exits that context. These distinct effects must not be merged into a universal release byte. The historical `xF1` STOP report conflicts with the later ROOT sweep's no-effect cell. See the [three matrices and ranked release hypotheses](XS8_COMMAND_COVERAGE.md#generic-key-release-hypothesis), [older `xFC/x9C` note](notes/kenwood-xs-reverse-engineering%20copy%207.md#L437-L445), and [October 12 physical report](notes/xs8-root-validation-2026-10-12.md).
