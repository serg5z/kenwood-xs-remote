# Source selection v1: evidence and controlled rollout

The service accepts `SELECT_SOURCE <name>` for the seven names below. It transmits the four ROOT commands established in the controlled ROOT + CD-playing sweep, and TV1/TV2 as one atomic CONTEXT transaction each (below). TAPE2 is not selectable as a source. The Gateway additionally requires its explicit `--enable-source` gate, verified nginx Unix-socket peer UID, authenticated identity, exact HTTPS Origin, a session-bound one-use CSRF token, and a fresh eligible service STATUS. The checked-in systemd unit has no control gate. Other Web controls have their own default-off gates ([Web API](web-api.md)).

All TX values here are **current logical TX bytes** (LSB first, short LOW = 0, long LOW = 1). Historical legacy TX converts as `logical = reverse8(~legacy)`. RX labels remain in their original decoder notation and are **not** converted with the TX formula. A received source broadcast or a TX waveform match does not prove that the receiver executed a Web request.

**TV1/TV2 transaction.** The Gateway sends one `SELECT_SOURCE TV1` (or `TV2`); it never sends the three frames itself. The service runs `0x17 → 0x78 → 0x07` (TV2: `0x88`) through VolumeControl's CONTEXT entry and exit, the same mechanism as MUTE: `context_may_be_open` is set before `0x17`, an unverified entry, key or exit frame latches `FAULT_LATCHED` after the exit is attempted (three attempts), and the key byte is never resent. Unlike MUTE it never cancels a hold: it answers `ERR VOLUME_BUSY` during any volume hold and `ERR CD_TRACK_BUSY` during any CD hold or pair, without transmitting. A shutdown signalled before the key byte replies `ERR SHUTDOWN` (the entry is undone if it was sent). The reply has the same `OK SOURCE_TX` / `ERR SOURCE_UNCERTAIN` form as the ROOT sources, and the Gateway allows 3 s for it.

The service rejects unknown names and TAPE2 without transmitting. It also rejects selection in BOOT_INHIBIT, FAULT_LATCHED, an unhealthy monitor, or any non-IDLE state with an outstanding STOP or possibly open context. It sends one ROOT byte without retry. `OK SOURCE_TX gpio_tx=TX_OK waveform=MATCH receiver_execution=UNVERIFIED` separates GPIO completion, observed matching bus waveform, and unknown receiver execution. `ERR SOURCE_UNCERTAIN` has no automatic retry. The Gateway limits source dispatch to one request per session per second; the Web UI also suppresses rapid repeat presses. The Web UI never marks a source as confirmed selected; it reports only the attempted transmission.

**CD auto-stop when leaving CD (Gateway only).** When the STATUS read for a source request reports `receiver_source=CD` that is **fresh** (observed within 30 s, `receiver_integrity=HEALTHY`) and the request selects TUNER, PHONO, TV1, TV2 or TAPE1, the Gateway first sends one `CD_STOP` (the same command as the Web STOP button, ROOT `0xA1`) and only after a verified `OK CD_TRANSPORT_TX action=STOP … waveform=MATCH` sends `SELECT_SOURCE`. Selecting CD never stops; an UNKNOWN, LAST_KNOWN (stale) or UNCERTAIN observation, or a non-CD source, selects without STOP; the TAPE2 MONITOR toggle is not a source request. The XS8 Service is unchanged and sees two ordinary commands.

- **Serialization.** The source request holds every Gateway control lock (CD, volume, POWER, MONITOR) from before its STATUS read until `SELECT_SOURCE` answers; a concurrent request is refused with `BUSY`/`CD_BUSY`/`VOLUME_BUSY` (the Gateway also serves one request at a time).
- **Gates.** The usual source eligibility (volume `IDLE`, healthy monitor, no STOP or CONTEXT obligation, CD idle with no owed release) applies; the STOP additionally needs CD STATUS fields (else `NOT_ELIGIBLE`) and the CD dispatch spacing (else 429 `TOO_FAST`). Nothing is sent on a refusal.
- **Failures.** If `CD_STOP` is rejected, times out, disconnects or is uncertain, `SELECT_SOURCE` is not sent: the reply carries `stage: "CD_STOP"`, `source_sent: false` and `physical_check_required` (false only for a clean refusal). A failure of `SELECT_SOURCE` after a verified STOP carries `stage: "SELECT_SOURCE"`, the `cd_stop` evidence and `physical_check_required: true`. Neither command is ever retried.
- **Success** answers `SERVICE_TX_OK` with the source evidence and `cd_stop` evidence; `receiver_execution` stays `UNVERIFIED` and nothing claims the changer stopped or the source changed. The Web shows `CD STOP TX REPORTED · <SOURCE> TX REPORTED · SELECTION UNVERIFIED`.

The observed source can lag the receiver (it changes only when a broadcast is decoded), so a recent front-panel change away from CD may still read as fresh CD and cause a STOP; a change to CD not yet observed causes none.

## Raspberry Pi deployment and rollback (manual, not performed here)

1. Review this table and run `make all && make test`, `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest tests.test_gateway`, `node tests/test_web_mute.js`, and `node tests/test_web_source.js` on the Pi. These are offline fake-transmitter/fake-socket checks. Confirm the existing HTTPS, Basic Auth, identity-header replacement, `SO_PEERCRED` UID, Origin and CSRF configuration as described in [MUTE rollout](mute-control.md). Confirm no Gateway TCP listener and no nginx worker access to the XS8 Service socket.
2. Arrange an attended maintenance window. Stop the manually managed `xs8-service`, update its executable from the reviewed build, and restart it under the existing operator authorization procedure. Do not change `--max-hold-ms`, wiring, RT priority, or CEC. Verify STATUS is `IDLE`, monitor `HEALTHY`, `stop_owed=0`, `context_may_be_open=0`; otherwise keep source disabled. The service does not automatically leave BOOT_INHIBIT.
3. Inspect `systemctl cat kenwood-xs-gateway.service` for its actual absolute repository path and existing `--enable-mute` flag. Add **only** `--enable-source` to the existing Gateway `ExecStart` via a reviewed systemd drop-in, retaining `--systemd-socket`, `--nginx-uid 33`, `--https-origin https://woodland-pi.local`, and `--enable-mute` if MUTE is currently enabled. Run `sudo systemctl daemon-reload` and `sudo systemd-analyze verify kenwood-xs-gateway.service kenwood-xs-gateway.socket`, then stop only the Gateway service; the next authenticated HTTPS request activates it. Do not change nginx or the Gateway socket unit.
4. Check `/api/v1/capabilities`: CD, TUNER, PHONO, TV1, TV2 and TAPE1 should be listed as available sources when the service is eligible, and TAPE2 as blocked. The TAPE2 MONITOR button stays disabled unless its own gate is enabled. Check MUTE still works in its previously authorized state. No page load or status request should dispatch source selection.

For rollback, remove `--enable-source` from the Gateway drop-in and restart/activate the Gateway. Verify `/api/v1/source` returns HTTP 501 and all source buttons disable. If the service executable is rolled back, first disable the Gateway source gate, then restore the previous reviewed executable using the existing service management procedure. The checked-in read-only Gateway unit and existing MUTE override should remain unchanged unless a full control rollback is intended. The SSH-tunnel read-only workflow remains available through the default loopback mode.

## Controlled physical validation checklist (future operator action)

- Use an attended receiver, low listening level, no moving volume motor, known ROOT/healthy service state, and a front-panel path to restore the input. Record the actual display/input, source before and after, service GPIO TX result, waveform result, and any RX frame separately.
- Test CD, TUNER, PHONO and TAPE1 one press each, beginning from a different known input. Verify the displayed input physically. Also check a repeat request from the already selected input, and one request after a prior MUTE toggle. A matching waveform is not a physical input confirmation.
- TV1/TV2: verify from at least two other inputs (including CD while playing) that the display changes to TV1/TV2, MUTE and volume still work afterwards, and ROOT `0x13` reports the new source. Keep TAPE2 blocked as a source. For later research, establish their TX waveform in a controlled ROOT state and characterize TAPE2 monitor on/off using the ROOT `0x13` second response plus direct physical observation. Do not replay early passive RX `EB/E7` as TX or infer their meaning from alternation alone.
- After each test, record unexpected input changes, CD transport activity, monitor toggles, lock effects, RX silence, or an uncertain transmission. Stop testing on any unexpected side effect and roll back the source gate before investigating.
