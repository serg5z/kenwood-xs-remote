# Live receiver status v1

The XS8 Service caches **observed** KR-V6070 source and TAPE2 MONITOR bytes. The cache starts UNKNOWN on every service start. Passive valid frames update it; an explicit authenticated `QUERY_STATUS` can initialize or reconcile it. Neither a sent source command nor a matching local TX waveform selects a displayed source by itself. The electrical origin of a later bus frame remains unattributed.

The six passive source legacy RX values are `71/73/79/7A/7B/7D` for VIDEO2/PHONO/TAPE1/VIDEO1/TUNER/CD. A successful ROOT logical TX `13` query uses the corresponding first legacy RX `11/13/19/1A/1B/1D`; its second response is `18` for MONITOR OFF or `14` for ON. Both MONITOR values are also recognized as passive observations. [October 11 physical report](../research/notes/xs8-readback-2026-10-11.md). RX values are later-decoder legacy labels, not logical TX bytes.

The service accepts only complete, valid known bytes. Frames belonging to a pending query are withheld from passive classification; locally transmitted frames are excluded by TX timing: each local frame only within its own transmit window, so a receiver frame between the frames of one multi-frame command (for example the source broadcast between `0x78`/`0x88` and the `0x07` exit of a VIDEO1/VIDEO2 selection) is still observed. A frame just after a local TX may be labeled `AFTER_LOCAL_TX`, which describes timing, not receiver acknowledgment. A successful query updates the cache only after its full observation window succeeds. A failed, missing, overlapping, extra, invalid, or gap-corrupted query leaves prior values untouched. A monitor gap, history overflow, or health failure marks retained values `UNCERTAIN`. If the monitor remains healthy after a cache-history overflow, a later fully valid query with both known fields can reconcile it; a monitor health failure stays latched and requires investigation and service restart, which initializes UNKNOWN.

`STATUS` retains its existing fields and adds `receiver_source`, `receiver_source_ns`, `receiver_source_evidence`, `receiver_monitor`, `receiver_monitor_ns`, `receiver_monitor_evidence`, and `receiver_integrity`. Timestamps are kernel monotonic nanoseconds. Evidence is `NONE`, `PASSIVE`, `AFTER_LOCAL_TX`, or `QUERY`; integrity is `HEALTHY` or `UNCERTAIN`. The Gateway presents the fields under `receiver` in `GET /api/v1/status`, with age and `FRESH` (30 seconds or less), `LAST_KNOWN`, `UNKNOWN`, or `UNCERTAIN` labels. Time alone never erases an observation. A service restart does erase its cache. No GET endpoint sends `QUERY_STATUS` or another XS8 frame.

**Local commands clear the affected field.** Once any frame of a local `SELECT_SOURCE` (including the VIDEO1/VIDEO2 CONTEXT sequences) or `TAPE2_MONITOR_TOGGLE` has been attempted, verified or uncertain, the service sets that field to `UNKNOWN`, `_ns=0`, evidence `NONE`, because what the receiver reports may have changed. Frames that began before that command's first TX frame can no longer set it; a broadcast during the command, a later passive report or a query can. A command refused before any TX clears nothing. The cleared value is kept as last-known for diagnostics only: the journal line `XS8 RECEIVER source|monitor cleared after local TX floor_ns=… last_source=… last_monitor=…` records it, and STATUS does not report it.

**Query outcomes.** A successful `QUERY_STATUS` replies `OK QUERY_STATUS reason=NONE`. Every other outcome is `ERR QUERY_STATUS reason=…` and records nothing:

| Reason | Meaning |
|---|---|
| `NO_REPLY` | Own `0x13` echo verified, then no frame at all in the 500 ms window (no gap, overflow or monitor fault) |
| `PARTIAL` | Echo, then exactly one frame |
| `TX_UNCERTAIN`, `TX_MISSING`, `TX_INVALID`, `TX_MISMATCH` | The query frame itself is unverified, unseen, invalid or a different byte |
| `OVERLAP`, `INCOMPLETE`, `EXTRA`, `OUT_OF_ORDER` | Colliding, invalid or partially received frames, more than two frames, or swapped fields |
| `EVENT_GAP`, `OVERFLOW`, `MONITOR_FAILED` | Lost edges, monitor history overflow or monitor failure |

`NO_REPLY` is evidence of silence only; it never by itself means the receiver is off.

**`QUERY_STATUS SETTLE`** is the same single query, sent only once the bus is quiet: no local TX for 600 ms and no bus frame for 200 ms, waiting at most 1.5 s (provisional values). 600 ms clears the changer's `0x94` report about 320 ms after a CD STOP, which otherwise lands in the query window and fails it as `EXTRA`. If the bus never goes quiet, the reply is `ERR QUERY_STATUS reason=BUS_ACTIVE` and nothing is sent. While it waits, it holds the same RX slot as a query (other controls get `ERR QUERY_STATUS reason=SESSION_BUSY`; `STATUS`, `RESEARCH_CONTEXT_STATUS` and `VOLUME_RELEASE` still answer), except that a `VOLUME_PRESS` or an exact `MUTE` (the CEC controls) preempts it: the waiting request gets `ERR QUERY_STATUS reason=PREEMPTED` with nothing sent and no automatic retry, and the press or MUTE then follows its normal path and safety gates (it may still be refused by them). Once `0x13` has been sent, both get `SESSION_BUSY` as before. Disconnecting, or sending anything else on the requesting connection, ends it without TX. Once the query frame is sent, the transaction is exclusive exactly like `QUERY_STATUS`. Plain `QUERY_STATUS` is unchanged.

`POST /api/v1/receiver/query` requires the independent, default-off Gateway `--enable-receiver-query` option. It accepts exactly `{}` with `application/json` after the same verified nginx peer UID, Basic Auth identity, exact HTTPS Origin, session cookie, and one-use CSRF checks as MUTE and SOURCE. It requires eligible IDLE/healthy service status, dispatches exactly one local `QUERY_STATUS`, never retries an uncertain outcome, and rate-limits repeat requests. The service remains the final safety gate. The Web SYNC button is disabled when authorization or service readiness is unconfirmed; page load and periodic polling never invoke it. With the same gate, the Gateway also ends every verified source selection and TAPE2 MONITOR toggle with one SYNC under that request's locks ([final SYNC](source-selection.md)); it is never sent after a failed or uncertain control, never retried, and a manual SYNC within 2 s of it returns 429. TAPE2 remains disabled as a source TX control even when its observed state is displayed.

## Raspberry Pi rollout and rollback (manual; not performed here)

1. Run `make all && make test`, `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest tests.test_gateway`, and `node tests/test_web_receiver.js` alongside the existing Web tests on the Pi. These are offline tests. Verify the current nginx HTTPS, Basic Auth, identity-header replacement, Gateway Unix-socket peer UID, and XS8 Service socket permissions before changing the live stack.
2. During an attended maintenance window, ensure no volume motor hold is active. Stop the existing XS8 Service using the local operator procedure, install the reviewed new executable, and restart it with the existing authorization and hold settings. Do not change GPIO timing, RT priority, wiring, CEC, or the motor configuration. Check `STATUS`: receiver source/MONITOR must start `UNKNOWN`; monitor must be `HEALTHY`, with `stop_owed=0` and `context_may_be_open=0` before considering SYNC.
3. Review `systemctl cat kenwood-xs-gateway.service` and preserve all current options. Add only `--enable-receiver-query` to the existing authenticated socket-activated Gateway `ExecStart`, keeping `--systemd-socket`, the verified `--nginx-uid`, exact `--https-origin`, and any existing MUTE/SOURCE gates. Run `sudo systemctl daemon-reload` and `sudo systemd-analyze verify kenwood-xs-gateway.service kenwood-xs-gateway.socket`; then stop only the Gateway service so the next authenticated request activates the new process. Do not change nginx or its socket unit.
4. Verify GET status and capabilities first: no XS8 TX should occur. The iPhone should show UNKNOWN before an observation and SYNC only when the service is eligible. A deliberate single SYNC should produce one logical TX `13`; compare reported raw frames, displayed receiver source, and MONITOR setting. Check a front-panel source change and both MONITOR changes update the page through passive observation on the next poll. Check unknown source TX controls remain disabled and existing MUTE/SOURCE behavior still works.

For Gateway rollback, remove `--enable-receiver-query` from the reviewed drop-in and restart/activate only the Gateway. Verify `/api/v1/receiver/query` returns HTTP 501 and SYNC is disabled; MUTE and SOURCE gates should retain their previous settings. If rolling back the service executable, disable the query gate first, then restore the previous executable using the existing operator procedure. A previous service has no receiver cache extension, so the new Gateway will report receiver UNKNOWN rather than inventing state. No deployment is performed by this document.

## Physical validation checklist

- Record the visible source and MONITOR state, service `STATUS`, raw decoded RX values and timestamps, validity, gap count, and any CD-player activity before and after one manual SYNC. Keep the receiver in known ROOT/IDLE with no active volume motion.
- Check each of the six source displays against its passive byte and first query RX; check MONITOR OFF/ON against `18/14`. Use front-panel changes independently of Web source selection so the cache cannot be mistaken for last-command echo.
- Check that an unrelated or invalid frame does not change the indication. If the monitor reports a gap or becomes unhealthy, verify the page marks retained observations uncertain and disables SYNC. Stop on an unexpected action.
- Repeat a query with the CD player idle and active to assess temporal attribution. Do not interpret extra frames as acknowledgments or silently attach them to the query.

**Remaining limits:** The source/MONITOR associations were physically validated on one KR-V6070, but the October 11 per-trial raw edge traces are not archived. Time proximity does not prove frame origin or receiver execution. `FRESH` means recently observed, not guaranteed current; missed passive events, a lost ground, or a failed receiver can leave last-known state wrong until a new valid observation. No absolute-volume, CD DIRECT, or SURROUND readback is established.
